# 日语朗读流水线：现状流程与实现总览

日期：2026-11-19 晚。本文档汇总现行流程、各组件的实现方法，以及 2026-11-19 晚讨论定下的全部修正细节，供审核。文中标注的为生产现状，的为已定稿待实施，的为当晚正在跑的设计任务。

## 一、总览：一篇文章的一生

```
存入原文 ──→ 生成骨架 ──→ 执行者补译 ──→ 校验入库 ──→ 播放合成
(/share) (TtsWeb) (API / agy) (commit) (Edge TTS + HLS)
partial 分句+分词 tr + fixes 新版本 边合成边播
可朗读 +读音+注音 status=ready
```

核心原则：**存原文与补译解耦**。原文一存入即可朗读（partial 保底），后续任何一步失败，文章不丢、照常可读；补译完成只是把同一短链的内容升级为 ready，短链永不变。

## 二、部署形态（三处）

| 位置 | 跑什么 | 角色 |
|---|---|---|
| 77B（云端） | TtsWeb（8791）、agnes-service（8793）、PostgreSQL `db77database.reading` | **唯一真源**：文章、骨架、译文都存这里 |
| ddPC（家里） | TtsWeb 同源副本、agy、电视控制 | 77B 文章的只读 SQLite 缓存（每小时拉取＋服务内预热，可离线播）；本地新存的文章只进本地 SQLite（简易模式，不回写 77B） |
| 本机 VM（A001） | agy、巡检、每日镜像 | reading 只读镜像（每日 04:27 从 77B 拉）；L2 巡检执行地 |

## 三、流程五步（实现方法）

### 1. 存入原文

- agent 通道：A001（sword 的文章）或 A003 糖糖（Tang 的文章）调 TtsWeb `POST /share`（令牌认证），交原文＋标题。
- 服务端处理：NFKC＋换行规范化 → 分句 → 生成骨架 → 按内容哈希去重（命中已有文章直接返回原短链）→ 落库为 partial，返回 10 位十六进制短链 `/?s=<id>`。
- 网页通道：见第六节，尚未上线。

### 2. 生成骨架（TtsWeb 本地完成，不调 AI）

- 实现：TtsWeb 的 `tokenizer.py`，进程内常驻 **fugashi（MeCab 封装）＋完整版 UniDic**。
- 产物三层：分句（带序号与字符区间）→ 每句分词 → 每个 token 带 {表层、原形、词性、UniDic 首选读音、ruby 注音}；ruby 由服务端按送假名对齐推导；词典查不到的 token 标 `unk`。
- 两个入口：`/share` 存入时生成并落库（partial 的骨架）；`POST /api/v1/ingest/preview` 现算返回、不落库（给执行者当工作底稿）。
- 保留：UniDic 给的是词典首选读音、不看上下文，地名/熟字训/多音字可能错或缺——留给第 3 步修正。

### 3. 执行者补译（全流程唯一用 AI 的一步）

契约（朗读设计 §2.2④，说明书在 TtsWeb 的 `/ingest.md`）：

- 执行者只回三样：每句译文 `tr`、读音修正 `fixes[{seq, tok_i, reading}]`、可选词义 `gloss`。**不许动原文与分词边界**。
- 硬规矩：通读全篇、带上下文整批翻译，禁止逐句孤立翻译；材料自带译文时只对齐不重翻（`tr_via='provided'`）。

执行者分级：

| 级 | 执行者 | 触发与速度 |
|---|---|---|
| L0/L1 | API 路：agnes-service 编排调 Gemini（主）/Agnes（兜底） | 服务端自动，无人参与；实测 Gemini 整篇 15 句 1.9 秒 |
| L2 | agy 的 Gemini agent 整篇接手重译 | API 结果校验不过/质量不行/熔断时才上；agent 调用量级，几十秒到几分钟 |
| L3 | 无（partial 保底朗读） | 前两级都失败时的兜底状态 |
| T 态 | 无（只重试） | TtsWeb/77B 不可用时，最长 24 小时 |

### 4. 校验入库（commit）

- 入口：`POST /api/v1/ingest/commit`（令牌认证，提交者身份由令牌定死，added_by 不可自称）。
- TtsWeb 服务端校验：句数对齐、fixes 下标与读音合法、`tr_via` 白名单；通过才写新 version、切换 current_version、status 转 ready。校验不过保持 partial。
- 补译走 replace 路径覆盖同一文章；`VERSION_CONFLICT` 视为「对方已完成」的收敛信号，不算失败。

### 5. 播放合成（播放时现合成，不预存音频）

- 播放页 `POST /play` 建会话 → 全文按句打包（≤2000 字/段）→ 微软 Edge TTS WSS 流式取音频（日语默认 ja-JP-NanamiNeural，语速默认约 80%）→ ffmpeg 边收边转 AAC、切 3 秒 TS 片，m3u8 动态追加、结束补 ENDLIST（HLS 方案，为治 iOS 裸流中途收尾而定案）。
- 平台分支：iOS/Safari、电视 webOS 走原生 HLS（webOS 另有结尾看门狗）；桌面 Chrome 走自托管 hls.js 从头播。
- 播放页 v3（Vue 3）：上＝当前句卡片（原文＋ruby＋句下译文），下＝全文列表（当前句高亮、点句跳转），注音/译文开关、选文列表、长句自动量测字号。**逐句高亮靠字数加权估算**，用 Edge 句边界做真实时间轴的 P3 已设计未实施，偶有小半句偏差。
- 推电视：ddPC 脚本打开短链页，播放前 setvol 12。

## 五、agnes-service 与 analyze 一期

- 服务：ASP.NET Core 10，77B 8793，JWT 认证照 dbapi（access 30 分钟＋refresh Cookie 7 天轮换、登录锁定、IP 封禁）；限额 10 次/分钟、200 次/天、单账号并发 2、全局 6（JST 00:00 重置）；调用记录存 `agnes_auth.call_log`（90 天清）；管理后台仅 admin。
- `POST /api/analyze` 两形状：raw（交原文，服务端分词骨架＋模型补读音/译文，短句用）、enrich（交骨架紧凑投影，服务端内部分块约 20 句、逐块校验修复，整篇用）。
- provider：**Gemini 主、Agnes 兜底**（2026-11-19 用户拍板换主）；Gemini 内 `gemini-flash-lite-latest` 优先（`gemini-flash-latest` 实测两次超时，不可用作默认）。注意 `.env` 的 ANALYZE_* 配置不吃热重读，改后须重启服务。
- 账号：MuseAgent1（id 29）＝A001、MuseAgent2（id 30）＝A003（agent 直调用，密码存本机文件、不入记忆）；ReaderNew（id 31）保留，第二期网页通道不用它。
- added_by 口径：按提交通道记真实提交者（agent 记 A001/A003、网页记登录名），另加 `added_via` 列区分来源（agent/web/legacy）。

### 实测结论（2026-11-19，北海道 15 句文）

- 速度：Gemini enrich 整篇 1.9 秒；Agnes enrich 199 秒。
- 读音：Gemini 98/99 与校对版一致、硬伤为零；Agnes 64/69、4 个硬伤。
- 译文：两家各有一次方向/逻辑小错，整体可用。
- **fixes 两家都不可靠**（都误改过大雪山「大」的读音）：只能当可疑清单，二期由 FixTriage 本地分流（词典复核），不自动落库。
- 上游限额：Agnes 免费 Key 文本有效 20 次/分钟，修复重试与模型兜底都计入，批量调用必须带间隔。
- 公网代理约 20 秒即断长请求：长调用一律走 77B 本地口；二期编排因此必须是异步作业，不能同步长调用。

## 七、今晚讨论定下的修正（2026-11-19 晚）

### 1. 播放与保存分离（原则）

播放界面就是纯播放，保存走另外的路子：保存页是独立页面、独立链路，播放页（8791 v3）不承载任何保存功能。此前定稿「播放页加添加文章按钮」的口径作废。

### 2. 网页保存认证：三版被否与现方向

被否的三版及原因：

- **浏览器带 TtsWeb 写令牌调 /share**：/share 是给 agent 用的机器接口、不公开；令牌写进页面等于公开，否。
- **TtsWeb 服务端保存入口＋保存口令**：口令只能用户自选——太长难记难输入（主要在手机上用）、太短不安全（页面在公网），长短两难，否。
- **口令走保险库**：保险库是给 agent 代登录用的，用户本人取不出明文；而网页保存场景没有任何 agent 在场，不成立，否。

用户的一个建议（非定案，设计中）：

- 用 8793 现成的 **JWT 登录**（用户自己的账号，就是平时登管理后台那个）认证「人」；
- 认证通过后，由**服务端节点**持复杂令牌代调 TtsWeb `/share` 完成保存——令牌只在服务端之间流转，用户永不接触；
- 文章 added_by 记登录名（不是固定账号；ReaderNew id 31 是已作废的「固定账号代存」方案的产物，保留不用）。
- 用户明确：这只是他提出的一个思路，不知道有没有更好的。已托 Claude 按**需求与环境**提最佳实现建议（Opus，任务书 `PHASE2-AUTH-DESIGN-PROMPT.md`）：先把需求与环境讲清、列候选比较，第一标准是**简单、不增加太多复杂度**，最后给出唯一推荐；上述 JWT 方案只是候选种子，可以被推翻。
- 时间：2026-11-19 22:45 发车，23:20 收件检查把摘要带回「Agnes API 测试」会话；设计经用户拍板后才回写定稿、才恢复实施。

### 3. L2 的「无人」问题与执行环境改定

- 问题：网页通道落 L2 时没有 agent 在场，原安排「A001 每日巡检在 ddPC 调 agy」等于依赖巡检者绕远路。
- 改定：**网页通道的 L2 待办，由 A001 巡检时用其自有 agy（本机 VM 本地）直接完成**，不再绕 ddPC。理由：巡检者本就是 A001，绕 ddPC 只增一跳延迟。
- agent 通道不变：A003 等发起者提交的文章落 L2，仍由发起者在 ddPC 调 agy 当场接手（ddPC 的 agy 是她够得着的执行环境）。
- 两处 agy 是同一个 Google 账号（proseidon@gmail.com），共用同一额度池（每日 09:00 额度检查照旧一份）；tr_via 均为 `agy-gemini`，记账无区别。

### 4. 巡检频率与时段

- A001 巡检 L2 待办：**每小时 1 次**（由每日加密，用户定），但**只在 08:00–24:00（JST）**，夜间 00:00–08:00 不巡。
- 后果：白天落 L2 最长等约 1 小时；夜间落的等到次晨 08:00 首巡。其间文章保持 partial 可朗读。
- 巡检定时任务随第二期上线时建立（接口未上线前不空转）；口径：清单为空静默，只在处理了或失败时报告。

### 5. 执行者：速度与「谁来调」

- 速度：API 路（Gemini enrich 整篇 1.9 秒）比 agent 路（agy/Claude 无头，几十秒到分钟级，且 Claude 有 5 小时额度墙）快一到两个数量级，故 API 为主力、agy 只作 L2。
- 谁调：API 路由 agnes-service 在服务端自动调，无人参与；agy 由 agent 调（网页待办归 A001、agent 通道归发起者）；**Claude 完全退出朗读流水线**（用户定，省着用），只作服务实现者。
