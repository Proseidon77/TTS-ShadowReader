# TASK6 第二期·网页保存认证设计（任务书）

日期：2026-11-19 晚。性质：**只做设计、产出设计文档，不动代码**。设计对象：第二期网页通道（/add 粘贴页保存文章）的**认证方式**。背景定稿：TASK6-PHASE2-PLAN.md（其 §1.5 的认证口径正被本设计替换，设计完成后由 operator 回写定稿）。

## 一、问题（用户原话提炼）

网页保存文章需要一道写权限门，卡在人机矛盾上：

- **人输的口令**：太长难记、难输入（用户主要在手机浏览器上用）；太短不安全（页面挂在公网地址上）。
- **机器用的令牌**：可以任意复杂，但不能写进页面、也不能让用户输。

此前两版口径都因此被用户否掉：①浏览器带 TtsWeb 写令牌调 /share（令牌进页面，不行）；②用户自选保存口令、TtsWeb 服务端比对（长短两难，不行）。

## 二、用户的一个建议（仅作候选种子，不是定案）

**注意定位**：下面只是用户随口提出的一个思路，他明确说不知道有没有更好的方法。你的任务不是论证或细化它，而是把第一节的需求与第三节的环境吃透，针对「网页保存文章」这一条路给出你认为**最佳**的实现建议——可以完全不用这个建议。

77B 上已有带 JWT 认证的后端（agnes-service，8793）。做**一个前端页面**：用户先通过该后端的认证（登录），认证通过后，由一个**服务端节点**持复杂令牌代调 TtsWeb 的 `POST /share` 完成保存。即：人只用自己本来就在用的 agnes-service 账号口令登录；复杂令牌只在服务端之间流转，用户永不接触。

**分离原则（用户 2026-11-19 确认）**：播放界面就是纯播放，保存走另外的路子——保存页是独立页面、独立链路，播放页（8791 v3）不承载任何保存功能与逻辑。此前定稿「播放页加『添加文章』按钮」的口径按本原则修正：按钮/入口不再属于播放页，设计时不要再往播放页里塞保存。

## 三、现状资产（设计必须基于事实，先核对代码再设计）

- **agnes-service（8793）**：完整 JWT 认证已上线——账号登录、access token 30 分钟、refresh httpOnly Cookie 7 天轮换、登录锁定与 IP 封禁、管理后台页面（用户日常已在浏览器登录使用）。账号体系现成：含 admin 与普通 user 账号。
- **TtsWeb（8791）**：`/share` 等写接口走 tokens.json 令牌认证，令牌可任意复杂（机器持有）；第二期本来就规划签发 `agnes-service` 令牌供 8793 调 preview/commit（见定稿 §5 DF-11），代调 /share 与之同路。
- **使用形态**：单用户个人工具，但 8791/8793 均有公网地址；用户主要在手机与电脑浏览器上操作。
- **既有编排**：保存后补译走第二期 ingest 编排（定稿 §2），触发方式在新形态下需重新接线（见设计问题 4）。

## 四、要设计的问题（逐项给出结论与理由，不要只列选项）

0. **核心任务：给出最佳实现建议（用户 2026-11-19 定调）**：基于第一节的需求与第三节的环境，把能解决矛盾的可行方法都列出来（包括但不限于第二节的用户建议），逐个按「新增组件/改动量、用户操作负担、安全强度、失败模式」比较，最后给出**唯一推荐**及其理由。**评判第一标准：简单可靠、不增加太多复杂度**——能复用现有资产（8793 的 JWT、8791 的令牌、现有页面与服务通道）就不新增；更复杂的方案必须说明为何值得，否则淘汰。以下 1–7 对最终推荐方案逐项落实（按推荐方案的实际形态等价落实，不要硬套用户建议的结构）。
1. **页面落点**：按分离原则，保存页独立于播放页。页面由 8793 同源直出（与管理后台同站，天然携带登录会话），还是另有更简的落法？正面处理 refresh Cookie 相关问题——注意：此前审核（PHASE2-REVIEW.md）指出过「/add 与 8793 主站共用 refresh Cookie 会互顶登录」的风险，本次形态下该风险是否成立、如何规避，须明确结论。
2. **保存动作的执行点与凭据**：保存最终由哪个进程、持什么凭据完成（代调 /share 或其他写入方式）？凭据如何做到不进页面、不经用户手。画清请求链：浏览器 → （哪台服务/哪个入口） → 保存 → 回短链。若推荐方案含登录态，写清校验方式（本地验 JWT / 会话 Cookie 等）。
3. **归属记账**：经此路保存的文章 added_by 记什么（登录账号名？）、added_via 记 web，与定稿 §1.5「added_by＝web」的旧口径如何衔接或修正，给出定值。
4. **补译触发**：保存成功后谁触发 ingest 编排（节点顺手触发 / TtsWeb 侧触发），链路与失败处理（保存成功但触发失败时文章保持 partial、不丢）。
5. **准入与防护**：哪些账号可经此路保存（任意 user？仅指定账号？要不要在用户表加开关）——按单用户个人工具的尺度给最简结论；CSRF 防护方式；登录侧已有锁定机制可否直接复用，不要新造。
6. **降级行为**：8793 不可用时 /add 能否保存、播放页阅读是否受影响，写清边界。
7. **与定稿的差异清单**：列明本设计使定稿 §1.5/§5 中哪些条款作废（如服务端保存入口、自选口令口径）、哪些保留（share-first、短链不变、按钮只上 v3、补译编排 §2 不动等），供 operator 回写定稿。

## 五、约束

- 不过度设计：单用户个人工具，不建新账号体系、不引入新中间件，能复用现成机制（JWT、refresh Cookie、登录锁定、服务令牌）就复用。
- 任何令牌/口令的**值**不出现在设计文档里，只记名称与存放位置。
- 本任务只产出设计文档 `PHASE2-AUTH-DESIGN.md`（放 agnes-service 项目内），含：候选方法比较、**唯一推荐（最佳建议）及其理由**、推荐方案的请求链图（文字即可）、接口契约草案、归属与准入定值、差异清单、实施要点清单。**不动任何代码、不改定稿、不碰生产。**
