# /add 文章管理区版面优化 — 报告（2026-11-20）

只改了前端 `index.html`。后端代码、接口、权限逻辑和 TtsWeb 都没动。后端的 PATCH 编辑接口和编辑作业流水线照旧在线上，只是页面上不再有入口。

## 0. 接手状态与选择

开始时比对了现行 `index.html` 和 `index.html.bak-20261120-uifix`：
- `.bak` 与当时线上的 `publish/index.html` 逐字节相同，就是版面优化前的生产版。按要求保留，没删。
- 上一轮中断时已经做完的部分：表格操作列移到第一列（colgroup 定列宽，`table-layout: fixed`），长单元格省略截断并加 `title`，窄屏改卡片布局，`main.wide` 扩展到 add 页签。还没做的部分：编辑按钮和编辑表单仍在，上一轮没有上线。
- **我选择在现状上续做，没有从 .bak 恢复重做。** 理由：已有改动逐行审过，方向和本任务一致，写法也对（全部用 textContent，权限判断没改）。缺的只是撤下编辑入口，外加一处断点修正（见第 4 项）。

## 改动点

### 1. 操作列放在行首，只留删除按钮
- 表头和每行的第一列都是「操作」，列里只有「删除」按钮。权限显隐没变：`can_manage` 为假时只显示「—」；删除前照旧弹 `confirm` 二次确认；所有文字照旧用 `el()` / textContent 写入，没用 innerHTML。
- 编辑相关的前端代码全部撤下：
  - 「编辑」按钮；
  - `#am-form` 编辑预填表单、`#am-out` 编辑作业输出区；
  - JS 里的 `amCount / closeEdit / 文章版 openEdit / stopAmPoll / renderEditJob / pollEditJob`，以及表单 submit 处理（PATCH 调用）；
  - `clearSession`、`deleteArticle` 里对上述函数的调用；
  - 只有编辑会用到的错误文案（job_active、version_conflict、title_required、invalid_text、invalid_lang、unknown_field）。
- 说明文字和 403 文案里的「删改」改成了「删除」。
- 状态列仍会显示后台作业标签（「处理中 / 编辑中 · …」）。这是只读的状态信息：如果有人通过 API 发起编辑，列表能如实反映。
- 顺带发现一个 bug：旧代码里有两个同名的 `function openEdit`，分别是文章编辑和「管理」页签的用户编辑，两者在同一作用域。函数声明提升后，后一个会覆盖前一个，所以原来的文章「编辑」按钮实际可能打开的是用户编辑弹窗。文章版这次已经撤掉，问题随之消失。用户管理的 `openEdit` 保持原样。

### 2. PC 宽屏用够空间：选**局部加宽**
- 容器宽度前后对比：

| 位置 | 改前 | 改后 |
|---|---|---|
| `main`（文本 / 图片 / 视频 / 我的账户 / 登录） | 860px | 860px（不变） |
| 「添加文章」页签 | 860px | 1440px |
| 「管理」页签（`main.wide`） | 1240px | 1440px |

- 做法：切换到 add 页签时给 `main` 加上 `wide` class（原来只有 admin 页签会加），同时把 `main.wide` 从 1240px 放宽到 1440px。直接打开 `/add` 时也会走 `selectTab("add")`，同样生效。
- 选局部而不是全局，理由：文本、图片、视频、账户几个页签都是单列表单，加宽到 1440px 后输入框和按钮会被拉得很长，反而难看。真正需要宽度的只有带表格的 add 和管理两个页签。管理页签一起从 1240 放宽到 1440，是为了两个宽页签切换时宽度一致；它的表格本来就有 `overflow-x:auto`，变宽只会更好。
- 1440 宽视口：内容几乎占满（左右各留 16px）。1920 宽视口：主栏 1440px 居中，两侧各留 240px，不再是中间一条窄列。

### 3. 桌面宽度下表格不出现横向滚动条
- `table.am` 用 `table-layout: fixed; width: 100%`，固定列宽如下，标题列吃掉剩余宽度：

| 列 | 宽度 | 内容估算（13px 字号） |
|---|---|---|
| 操作 | 72px | 删除按钮约 48px |
| 状态 | 130px | |
| 添加者 | 160px | |
| 添加时间 | 140px | 「2026/11/20 00:03」约 110px |
| 句数 | 52px | 右对齐 |
| 短链 | 170px | |
| **固定列合计** | **724px** | |

- 所有单元格都是 `nowrap + overflow:hidden + text-overflow:ellipsis`，并带 `title=` 全文，悬停可看。窄列内容都在列宽之内，不会换行。
- 短链的 `href` 不变，链接文字缩成 path+query（如 `v3?s=8b37ef919e`，各行主机名相同），悬停 `title` 显示完整 URL。
- 1440×900 时的核算：表格可用宽度 = 1440 − 2×16（main 内边距）− 2×15（卡片边框＋内边距）= 1378px，标题列 = 1378 − 724 = 654px。整表一屏放得下。固定布局下表格宽度不会超过容器，所以不会有横向滚动。

### 4. 手机端不回归（并修了一处边界）
- 窄屏下切换成卡片布局：每篇文章一张卡片，删除按钮在卡片顶部，其余字段带「状态：」「短链：」等标签。标题允许折行，长短链省略截断。卡片全部是 block 布局、宽度 auto，390px 下没有横向溢出。
- **边界修正**：上一轮写的卡片断点是 `max-width: 720px`。按上面的列宽核算，视口在 721 到约 965px 之间时，标题列宽度会变成负数，固定布局会把表格撑出卡片，平板宽度下会出现横向溢出。所以断点改成 `max-width: 980px`：980px 以上标题列至少有约 194px，980px 以下用卡片布局。这个媒体查询里只有 `table.am` 的规则，不影响页面其他部分。
