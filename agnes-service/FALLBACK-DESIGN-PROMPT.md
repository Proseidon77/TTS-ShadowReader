## 设计必须回答的问题

1. **分级定义**：给出 L0（正常）/L1/L2（及与原有 partial/raw 降级的关系）的明确定义。参考口径（可调整并说明理由）：L1 = API 路内部降级（换 provider、换模型、按块重试、缩小块、partial 提交）；L2 = API 路整体放弃，原有驻地方案接管。每一级写清：触发条件、进入后做什么、成功标准、再失败往哪掉。
2. **故障分类与判定**：哪些失败算「API 失效」（上游 401/403 配额类、密钥失效、5xx、超时、agnes-service 本身不可达、返回校验长期不过），各自在 L1 内处理还是直接触发 L2；判定者是谁（调用 ingest 的 agent？agnes-service 自己？给出依据——注意 agnes-service 叫不动驻地 Claude，切换决策点要落在真实存在的角色上）；连续失败的熔断与冷却（阈值、冷却时长、半开试探），避免每篇文章都先在死掉的 API 上白等一轮。
3. **时间预算**：每一级的超时与总预算（结合评审 B6 的分块与 INGEST_DEADLINE_S），给出「一篇新文章从 /share 到 ready 的最坏耗时」在各级下的估算；并说明降级对用户感知的实际影响（短链立即可用、译文是异步补齐的，降级主要影响译文就绪时间）。
4. **交接语义**：API 路死在半途（preview 已做、enrich 做了一半、commit 未成）时文章处于什么状态；驻地接管时如何安全续作（content_hash 去重、base_version、重复 commit 的收敛、已部分翻译的块要不要复用）；tr_via/tr_by 如何记录每一手的出处，混合作业（一半 API 一半驻地）时版本与出处怎么记才不乱。
5. **备份保鲜**：原方案要「随时能顶上」需要哪些保鲜措施——驻地令牌有效性、/ingest.md 时效、定期演练（频率、用什么文章、谁触发、结果记在哪）；API 路一侧的健康探针（/health 的 analyze 段、周期性真实小调用的配额代价）同理。给出可落地的最小保鲜清单，不要设计一个没人执行的复杂运维体系。
6. **两边各要改什么**：分别列 TASK6 侧增量（错误码要能区分可重试/致命、健康信号、幂等要求等）、朗读方案侧增量（执行者顺位的改法、design_proposal 修订注记的拟稿文字、/ingest.md 执行者一节的改法要点）、以及调用方（agent 入库手册/流程）的改动。每项标注是「实现前必须定」还是「可后补」。
7. **不做什么**：明确排除项（如自动在两套系统间双写、让 agnes-service 直接调度 Claude 会话等），并说明理由。
